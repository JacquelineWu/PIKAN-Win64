# PIKAN · Windows 版（ACDSee 风格看图软件）

> **开源许可：[MIT](./LICENSE)** · Copyright (c) 2026 JacquelineWu (flyercat)
>
> 本仓库是 [PIKAN-HarmonyOS](https://github.com/JacquelineWu/PIKAN-HarmonyOS)（ArkTS / ArkUI）的
> **Windows x64 移植版**，用 **C# + WPF（.NET 10）** 重写。
> 鸿蒙版已加为 git 远端 `harmony`，可随时对照两边实现。

界面布局与鸿蒙版一致（ACDSee 风格）：

- **顶栏**：标题 + 当前文件名 + 打开图库 / 选择图片 / 选择文件夹 / 回到上次 / 全屏 / 幻灯片
- **左侧**：**文件浏览器**（纯文件名列表，不显示缩略图）—— 顶上「..」回上级，中间是当前目录的子文件夹，
  再往下是这一层的图片；点图片右侧立刻显示，点文件夹就进到那一层。带排序控件
- **右侧**：大图预览区（画布底色 `#5F5F5F` 中灰），左上角信息浮层 + 右下角缩放角标
- **底栏**：状态栏（含 GPU 状态一行；CUDA 开关按钮已取消，需要时用 `Ctrl + G` 切换）

### 预载：翻页不等解码

后台把当前位置**前后各 50 张**（共 101 张）预先解码并缓存，切图命中就直接上屏：

| 情况 | 行为 |
|---|---|
| 命中预载缓存 | 立即显示（已是「可显示清晰度」）。缓存档位已覆盖屏幕所需像素时**不再二次解码** |
| 未命中（跳转 / 首屏） | 先解 768px 低清占位避免空白，同时解全清覆盖 |
| 放大查看 | 屏幕所需像素超过缓存档位时才补解一张全清（画布长边 ×1.5） |

- 缓存档位按「画布长边 × DPI × 1.15」取，**量化到 256 的倍数且向上取整**，
  夹在 1024–1536。向上取整很关键：向下取整曾把 1133 算成 1024，反而小于屏幕实际
  要显示的 1196 像素，于是每张命中缓存的图都还得再解一次全清——大图那一次要 1.5 秒，
  这就是切图卡顿的真正来源。
- 是否补解全清，比较的是**屏幕实际要显示的像素**（`ShowNeed`，含 zoom 与 DPI，留 5% 余量），
  而不是拿缓存档位去和带缩放余量的 ViewEdge 硬比——后者会一律判成"不够"，白白多解一轮。
- 内存：101 张 1536px 档约 640 MB（1200×800 的小图实测 367 MB）；另有 112 张 / 768 MB 双重淘汰保险。
- 窗口跟着位置滑动（`EvictOutside`），翻一整个大图库内存也不随翻页累积。
- **窗口是环绕的**：图库本就是循环的（翻过最后一张回到第一张），
  所以预载窗口也绕回——停在第 134 张时，第 135、136 **和** 第 1、2、3 张都在窗口里。
  否则每次跨过首尾边界都要重新解码一批图，绕回第一张时会明显卡一下。
- 状态栏实时显示「预载 N 张 · xx MB · 显存 N 张 xx MB」。

### 显存常驻：切图时尽量不要再计算

解码只是第一层。真正让切图"零等待"的是把解码结果**留在显存里**：

| 层 | 存什么 | 命中时省掉什么 |
|---|---|---|
| ① 显存常驻（`GpuImageCache`） | 预载解码后的 BGRA，一份设备指针 | 每次的 `CopyPixels`（CPU 拷几 MB）+ PCIe 上传（H2D） |
| ② 结果缓存（`GpuResampler`） | 某张图在某个目标尺寸下的成品位图 | 连 kernel 都不跑，直接把上次算好的位图拿出来 |

预载链每解码一张就顺手把它传进显存（`Put`），于是翻到它时 kernel 直接从显存取源；
换图库 / 档位变化时整批释放（`Clear`）。

**配额**：默认可占用显卡总显存的 **50%**（`--vram=N` 覆盖，N 为百分比，夹 5–80）。
配额不是预留——只有真的缓存了图才占，所以不会一上来就吃掉半个显存。
它每次会按当前空闲显存重算（500 ms 一节流），别的程序把显存吃了我们就往回收，
留 1 GB 安全垫；下限 640 MB，刚好保住一个满档预载窗口（101 张 / 610 MB）——
低于这个数窗口里的图会被 LRU 挤掉，翻回去还得重传，反而更卡。

**关键点：翻过的图不再被窗口淘汰。** 原先每翻一页就把离开窗口的图 `cuMemFree` 掉，
于是缓存大小恒等于窗口大小（101 张），配额给到 50% 也用不上。
现在改由配额 + LRU 兜底：翻过的继续留着，往回翻零成本；
一直往前翻则挤掉最旧的，总量停在配额处，不会失控。

- 结果缓存 12 张（约 48 MB 主机内存），LRU。
- 档位（edge）变了就整批作废——旧档位的图留着只会占显存。
- `--novram` 关掉这两层，回到"每次上传重算"的旧路径。
- `--tightvram` 回到"紧跟随窗口"的旧淘汰行为，用于 A/B 对比。

实测（`--bench`，同一批 16 次精修）：

| | 次数 | 合计 | 平均 | 最大 |
|---|---|---|---|---|
| 缓存开启 | 16（其中 12 次结果命中、4 次显存命中） | **12 ms** | 0.8 ms | 7 ms |
| `--novram`（旧路径） | 16（全是现场上传） | 166 ms | 10.4 ms | 15 ms |

即：再来回翻同一批图，重采样基本不花钱（结果命中 0 ms）。

### 上屏：零拷贝直通（D3DImage），复用位图兜底

最优路径现在是 **CUDA 直接写 D3D9 纹理 → WPF `D3DImage` 显示**（`D3dView.cs`）：
kernel 结果全程不离开显存，连"回读进 WriteableBitmap"这一步都省了。
落地只剩一次标脏区，实测 0 ms。

同一台机器 20 张 1920×1080 精修到 1232×770，各 76 次采样：

| | 重采样 | 落地/上屏 | 合计 |
|---|---|---|---|
| 零拷贝（D3DImage，现在） | 2.88 ms | **0.00 ms** | **2.88 ms** |
| `--nod3d`（复用位图） | 2.76 ms | 1.89 ms | 4.66 ms |
| `--noreuse`（每次新建位图） | 3–8 ms | 0 ms | 3–8 ms |

首次（源还没进显存）三种路径都是约 20 ms，差别只在之后的每一次。

零拷贝的硬前提：**CUDA 设备和 D3D9 设备必须是同一块 GPU**。混合显卡笔记本上
D3D9 的适配器列表只包含"有输出"的适配器，独显休眠时根本不在列表里。程序会在
互操作失败时自动向 Windows 图形首选项申请高性能 GPU（写 HKCU
`UserGpuPreferences`，`--nogpupref` 关闭；用户手动设过的不覆盖），**下一次启动**
D3D9 就能枚举到独显、通道自动建立。单 NVIDIA 独显的台式机第一次就能直通。
以上任何一步失败都安静回退复用位图，功能无损。

> 排查提示：如果 gpu.log 出现 `RegOpenKeyEx=5` 且令牌诊断显示
> `完整性=S-1-16-4096`（低完整性），说明 exe 文件被打了低强制标签（某些受管控的
> 工作目录会整棵树继承），此时写不了 HKCU。把程序拷到别处运行即可恢复，
> `Publish.ps1` 出包时也会自动把标签拉回 Medium。

### 放大：按需重新取样，不拉伸糊掉

过去长按放大只会把「适应窗口」那一档位图越拉越大——天性会糊。
根因是两条：

1. `RefineViewAsync` 里只要「目标 ≥ 位图尺寸」就 `return`（注释写着"放大不做精修"）；
2. 解码档位 `ViewEdge()` 只按**画布**算，完全不知道 `_zoom` 存在，
   于是放大后再补解一张，拿到的还是同一个不够用的档位。

现在的链路是：

| 情形 | 做法 |
|---|---|
| 屏幕需求 ≤ 手上位图 | GPU（或 AVX2）Mitchell **降采样**到正好等于屏幕像素，WPF 拿到 1:1 位图不再二次插值 |
| 屏幕需求 > 手上位图，且还能从原图取到更多像素 | **回解码器按新需求重新取一张**（`UpgradeViewAsync`），这才是「放大时再次 sample」 |
| 手上已经是原图全像素（≥ 100% 放大） | 到此为止，剩下的交给 WPF 插值（`BitmapScalingMode=HighQuality`） |

档位算法 `DecodeEdgeFor(need, 原图)`：`need` = 可用框长边 × DPI × zoom × 1.05，
夹在 `[ViewEdgeMin, ZoomEdgeMax=8192]`、不超过原图像素（解更大毫无意义），
再按单张 64 MP（≈256 MB）的预算收一收。

### 设备像素对齐（缩图不发糊的最后一环）

精修成品就算拿到了 1:1 的位图，也可能被 WPF 再糊一遍：画布尺寸常是小数
（如 1151.2 DIP），Uniform 布局算出的图片矩形落在 400.2px 这种**半个像素**上，
WPF 只好把整张成品再重采样一遍（Fant + 半像素相位），凭空发软。

对策（`ApplyViewGeometry` / `BakeZoom`）：

* `CanvasArea` 开 `UseLayoutRounding`，主视图改 `Stretch=Fill` + 显式宽高，
  宽高 = **取整后的适应矩形**（设备像素）÷ DPI；
* 缩放停稳（`ScheduleRefine`）时把 zoom「烤进」布局宽高（`BakeZoom`），
  RenderTransform 只剩镜像 ±1——布局取整是 WPF 里唯一能把显示矩形
  钉到整数设备像素的手段，RenderTransform 取不了整；
* 滚轮/捏合一动就「解冻」（`UnbakeZoom`），缩放反馈依然即时；
  精修目标 `TargetPixelSize` 与烤入宽高按同一规则取整，保证严格 1:1。

实测（1439×959 画布、DPI 1.25、4672×7008 原图）：适应 / 200% / 50% / 25%
四档的成品位图与屏幕矩形全部 **采样倍率 1.000、原点整数**——
屏幕上显示的就是 GPU Mitchell 的输出本身，一个插值像素都没有。

自检（`--zoomtest <图片>`，4672×7008 的原图，125% DPI）：

| 档位（界面显示的 %） | 屏幕需要 | 手上位图（档） | 拉伸比 |
|---|---|---|---|
| 13 %（适应窗口） | 596×894 | 596×894（2355） | 1.00 |
| 25 % | 1168×1752 | 1168×1752（2355） | 1.00 |
| **100 %（1:1）** | 4672×7008 | 4672×7008（7008，已是原图） | **1.00** |
| 200 % | 9344×14016 | 4672×7008（7008） | 2.00 · 已到原图像素上限 |
| 400 % | 18688×28032 | 4672×7008（7008） | 4.00 · 同上 |

100% 是分水岭：在这以内，屏幕上每个像素都对应原图的真实像素（缺的会先重新取样补齐）；
超过 100% 之后，屏幕要的像素比原图还多，多出来的信息并不存在，只能插值——
任何看图软件在这里都到顶，不是缺陷。

### HEIC / HEIF 说明

解码依赖系统装的 **「HEIF Image Extensions」**（Microsoft Store，免费）。
本机已装（`Microsoft.HEIFImageExtension`），所以 **无需 libheif 之类的第三方库**，项目零 NuGet 依赖。
没装的机器上 HEIC 会解码失败并在状态栏提示，其余格式不受影响 —— 与鸿蒙版依赖系统 codec 的行为一致。
同理 WEBP 依赖「Webp Image Extensions」（本机也已装）。

### 位置记忆：记住目录，重新扫描后再对位

退出时（含 `Esc` 关闭、点右上角 ✕）把三样东西写进 `%LOCALAPPDATA%\PIKAN\state.json`：

| 字段 | 内容 |
|---|---|
| `LastRoot` / `LastKind` | 上次浏览的**目录**，以及来源类型（`gallery` 图片库 / `folder` 文件夹 / `files` 手工挑的文件） |
| `LastIdx` / `LastUri` / `LastName` / `LastCount` | 停在第几张 + 那张的完整路径（两者互为校验） |
| `Snapshot` | 上次会话的图片列表快照（上限 600 条） |

下次打开**自动恢复**，优先级逐级下降：

1. **重扫目录**（`folder` / `gallery`）：后台 `ScanFolder` 再走一遍，新增/删除的照片自然反映出来；
   按 `LastUri` 路径精确对位 → 找不到且总数没变才按序号回退 → 都没有就停在第 1 张。
   为什么不能直接沿用快照：快照最多 600 条，大图库必然不全，而且它是死的，不会随目录变化更新。
2. **退回快照**：目录已被挪走/删掉，或上次来源是 `files`（手工挑的散图，按目录重扫会把没挑过的图也带进来）。
3. **都没有**：保持空态，状态栏提示重新选择。

细节：

- 扫描期间用户抢先点了别的图库 / 文件夹 → 恢复**自动作废**（`_userLoaded`），不会覆盖用户的选择。
- 列表为空时**绝不覆盖** `LastRoot` 与快照：否则一次「没加载出图」的会话会把上次的记忆抹掉。
- 恢复过程在后台线程，启动只多花一次目录扫描（几千张图通常几百毫秒），不挡窗口显示。

## 构建与运行

```bat
dotnet build -c Release
bin\Release\net10.0-windows\PIKAN.exe
```

需要 **.NET 10 SDK**（`net10.0-windows`，含 WPF / WindowsDesktop 运行时）。
本仓库用 Visual Studio 2026 / `dotnet build` 均可，无第三方包，restore 秒过。

### 便携版（唯一的发布形态）

`portable\PIKAN.exe` 是**自包含多文件版**（整个目录约 155 MB）：

- 目标机**不用装 .NET**，也不用装 CUDA Toolkit
- **不做运行时自解压**——不往 `%TEMP%` 写一个字节，双击即开
- 已做代码签名（见「SmartScreen 拦截怎么办」）

把整个 `portable` 文件夹拷到 U 盘 / 别的 Win64 机器即可，双击里面的 `PIKAN.exe` 就用。

一键出包（编译 → 发布 → 签名）：

```bat
pwsh .\Publish.ps1
pwsh .\Publish.ps1 -NoSign        :: 只发布，不签名（本机快速调试）
pwsh .\Publish.ps1 -Out D:\PIKAN  :: 输出到别处，例如直接发到 U 盘
```

它等价于下面这几步：

```bat
dotnet publish -c Release -r win-x64 --self-contained true ^
  -p:PublishSingleFile=false -p:DebugType=none -p:SatelliteResourceLanguages=en -o portable

pwsh .\Sign.ps1
```

**为什么不再发单文件 exe**：单文件版启动时必须把 WPF 的 native 组件
（`wpfgfx_cor3.dll`、`PresentationNative_cor3.dll`、`D3DCompiler_47_cor3.dll` 等）
自解压到临时目录。这一步一旦被安全软件或目录权限拦住，进程会在托管代码**之前**退出，
而 WPF 程序没有控制台，错误文本无处显示——表现就是「双击毫无反应」。
本机稳定复现过 `Failed to create directory [...] Error code: 5`（`%TEMP%` 不允许建提取目录）。
便携版不做自解压，这条失败路径根本不存在，代价只是目录里多一堆 dll。

几个已知事项：

- PTX kernel 已**嵌入程序集**（`EmbeddedResource`），任何形态都读得到；
  想换 kernel 调试就在 exe 旁边放 `Kernels\pikan.ptx`，会优先用外部的。
- 目标机上 GPU 加速要生效，需要 NVIDIA 驱动（Volta 及以上）；否则自动回落 CPU，功能不受影响。
- 看 HEIC 需要目标机装微软的 **HEIF Image Extension**（微软商店免费）；
  WEBP 同理需要「Webp Image Extensions」。

### 双击后毫无反应 / 闪退怎么办

便携版不做自解压，所以**历史故障（单文件版自解压被拒）已经不存在了**。
如果仍然打不开，按下面顺序定位：

1. **看崩溃日志**：`%LOCALAPPDATA%\PIKAN\crash.log`。凡是进入 `App` 之后的未处理异常
   都会写这里并弹窗，不会"静默闪退"。
2. **在 PowerShell 里跑一次**，把本来看不见的 host 层错误抓出来：

   ```powershell
   & .\portable\PIKAN.exe 2>&1
   ```

3. **看 Windows 事件日志**：应用程序日志里的 `.NET Runtime` / `Application Error`，
   以及 GPU 相关的看 `%LOCALAPPDATA%\PIKAN\gpu.log`。

程序侧已加固：未处理异常会弹窗提示并写入
`%LOCALAPPDATA%\PIKAN\crash.log`，不会再"静默闪退"；CUDA 探测也挪到了后台线程，
驱动初始化再慢也不会拖住窗口显示。

### SmartScreen 拦截怎么办

首次运行时 Windows 可能弹「Windows 已保护你的电脑 — Microsoft Defender SmartScreen 阻止了无法识别的应用启动」。
**这不是病毒告警**：exe 没有数字签名，SmartScreen 查不到发布者信誉，一律拦。三种处理方式：

| 方式 | 适用 | 怎么做 |
|---|---|---|
| 临时放行 | 偶尔用一次 | 弹窗上点 **更多信息 → 仍要运行**，之后 Windows 会记住这个文件 |
| 自签证书（已做） | 自己的多台机器 | 见下，拷 exe 时带上 `PIKAN-CodeSigning.cer` |
| 购买代码签名证书 | 对外公开发布 | OV 证书约 ¥1000–3000/年；EV 还能立刻建立 SmartScreen 信誉 |

**发布出的 `portable\PIKAN.exe` 已签名**：SHA256 + DigiCert RFC3161 时间戳，发布者
`CN=JacquelineWu (PIKAN)`，有效期至 2031-10-27（有时间戳，证书过期后签名依然有效）。

拷到另一台机器时，把 `PIKAN-CodeSigning.cer` 一起拷过去并执行：

```bat
certutil -addstore -user Root PIKAN-CodeSigning.cer
certutil -addstore -user TrustedPublisher PIKAN-CodeSigning.cer
```

重新编译后要重签：

```bat
pwsh .\Sign.ps1                :: 签 portable\PIKAN.exe
pwsh .\Sign.ps1 -Force         :: 强制重签
pwsh .\Sign.ps1 -NewCert       :: 换一张新证书
```

`Sign.ps1` 会自动找 Windows SDK 的 `signtool`、取/建证书、导入信任链、导出 `.cer`、签名并验证。

> 说明：自签证书只解决「自己机器上的信任」。SmartScreen 的信誉还看微软云端对该签名的统计，
> 自签证书在陌生机器上**仍可能提示**，点「仍要运行」即可；要彻底消除只能买受信任 CA 签发的证书。
> 签名只是往文件尾部追加签名块，不改变程序代码——已验证签名后 CUDA 链路照常工作。

## GPU 加速（CUDA 优先）

PIKAN 自带一层 CUDA 加速：**不装 CUDA Toolkit、不引任何 NuGet 包**，
直接 P/Invoke 驱动自带的 `nvcuda.dll`（CUDA Driver API），把手写的 PTX 交给驱动 JIT 编译执行。

```
GpuAccel.cs       CUDA 上下文 + PTX JIT + kernel 调度 + 设备缓冲复用（失败自动降级）
GpuResampler.cs   BitmapSource ↔ CUDA 的桥接，不可用时回落 WIC
Kernels/pikan.ptx kernel 源码（文本，随输出目录复制，驱动运行时 JIT）
```

### kernel

| kernel | 用途 | 说明 |
|---|---|---|
| `resize_mitchell` | 主视图精修 | Mitchell-Netravali，带 area sampling（缩放比越大核越宽，抗走样），每方向最多 16 taps，权重归一化 |
| `resize_bilinear` | 兜底重采样 | 结构最简单，Mitchell 不可用时顶上 |
| `gauss_h` / `gauss_v` | 分离高斯模糊 | 权重由 host 预计算后上传，半径取 3σ。原用于切图对焦动画，该动画已取消，kernel 保留备用 |

### 介入点

1. **主视图精修**：清晰图解码完成后，GPU 把它重采样到「屏幕实际显示像素」尺寸
   （原图尺寸 × FitFactor × zoom × DPI）。输出恰好等于显示像素，WPF 不再二次采样，
   且降采样用的是 Mitchell 而不是 WPF 的插值 —— 缩放/旋转停止 140ms 后重做一次，连续操作只保留最后一次。
   放大不精修（那只会凭空造像素），交给 `RenderTransform`。
2. ~~切图对焦动画的模糊~~ —— **已取消**（见下）。CUDA 高斯 kernel 仍在 PTX 里，随时可接回来。

### 降级：CPU 上的 AVX2 Mitchell

CUDA 不可用（无 NVIDIA 卡 / 驱动太旧 / PTX 加载失败）时**不降画质**——
精修改由 `CpuResampler` 在 CPU 上跑同一套 Mitchell-Netravali：`System.Runtime.Intrinsics`
的 AVX2 + FMA，分离式两趟（水平 → 垂直），权重表预计算并紧凑打包。
没有 AVX2 的机器再退到标量版，最后才落回 WIC。

高频测试图（3px 棋盘 + 细条纹 + 噪点，1536×960 → 983×614）实测：

| 实现 | 耗时 | 与 CUDA 版逐字节平均差 | PSNR |
|---|---|---|---|
| CUDA（PTX kernel，2D 卷积） | 2–3 ms | — | — |
| **CPU AVX2（分离两趟）** | 20–23 ms | **0.38**（最大 1） | 52.4 dB |
| WIC `TransformedBitmap` | 5–8 ms | 9.06 | — |

也就是说：**WIC 快 3 倍，但画质明显不如**；CPU 版在高频细节上几乎复刻了 CUDA 的结果
（差 0.38 个灰阶，肉眼不可见）。`--cmp` 会把这三个数都量出来。

### 开关

- 顶栏 `CUDA` / `CPU` 按钮点击切换，**Ctrl+G** 同效，状态栏右端显示当前后端与设备名
- 启动参数 `--nogpu` 强制 CPU 渲染（走 AVX2），便于对比
- 启动参数 `--noavx` 关掉 CPU 的 AVX2 Mitchell，回落到 WIC 双线性
- 启动参数 `--novram` 关掉显存常驻 + 结果缓存，用于对比缓存收益
- 启动参数 `--vram=50` 设定显存缓存可占总显存的百分比（默认 50，夹 5–80）
- 启动参数 `--tightvram` 让显存缓存紧跟随窗口（旧行为），用于对比「留住翻过的图」的收益
- 启动参数 `--nowrap` 让预载窗口回到线性截断，用于对比「窗口环绕」的收益
- 启动参数 `--noreuse` 关掉复用位图，回到「每次新建 BitmapSource」的旧路径
- 启动参数 `--nod3d` 关掉 D3D9 零拷贝通道，强制走复用位图
- 启动参数 `--nogpupref` 禁止程序自动向 Windows 图形首选项申请高性能 GPU
- 启动参数 `--cmp <图片或目录>` 自检：同一张图分别用 GPU / CPU / WIC 重采样，
  比对逐字节差异与耗时，结果写进 `gpu.log` 后退出（不弹窗口）
- 启动参数 `--zoomtest <图片>` 自检：逐档（适应 / 25% / 100% / 200% / 400%）打印
  「屏幕需要多少像素 vs 手上位图有多少」，拉伸比 > 1 就是会糊，写 `gpu.log` 后退出
- 启动参数 `--sorttest <目录>` 自检：把这个目录下的名称按「逐字符/自然序 × 正序/倒序」
  四种方式各排一遍写进 `gpu.log` 后退出，用来确认 `(1) (2) (11)` 到底排对了没有
- 诊断日志写在 `%LOCALAPPDATA%\PIKAN\gpu.log`（只记初始化与异常，正常路径几乎不写盘）

> 一个坑：CUDA 初始化要 1~2 秒。凡是**界面上**读 GPU 状态的地方都用
> `GpuAccel.IsReady`（不触发初始化），否则 UI 线程会被这 2 秒整个卡住
> （实测启动冻结 2 秒，就是状态栏绑定同步等 init 造成的）。
> 初始化交给后台 `InitGpuAsync`，完成后再刷新一次界面。

PTX 的 `.target` 会在加载失败时按 `sm_86 → sm_75 → sm_70` 依次改写重试，
覆盖 Volta 及之后的绝大多数 NVIDIA 显卡。

### 切图性能实测（`--bench`）

给切图链路加了分段计时（`Perf.cs`），`PIKAN.exe --bench` 会跑 2 轮「前进 20 张 + 原路后退
20 张」，再跑一轮**冷区轮**（跳到未预载处后立刻 40ms 间隔连滚，模拟最坏的未命中场景）
和一轮**滚轮轮**（抛真实的 `MouseWheel` 路由事件，走与用户滚滚轮相同的代码路径），
把各段耗时写进 `%LOCALAPPDATA%\PIKAN\perf.log`，测完自动退出。
往返跑是为了让同一批图被经过多次——这正是显存 / 结果缓存要覆盖的场景。
日常运行不打点、不写日志（要开就设环境变量 `PIKAN_PERF=1`）。
另有帧间隔监控，UI 线程冻结超过 50 ms 记一笔。

日志里每条重采样都标了来源，一眼看出走了哪条路：

```
GPU 重采样[结果缓存] 1087x1536 → 588x830  0 ms     ← 零计算
GPU 重采样[显存命中] 1280x853 → 1232x821   7 ms     ← 源已在显存，未上传
GPU 重采样[常规上传] 1280x853 → 1232x821  15 ms     ← --novram 时的旧路径
CPU 重采样[CPU/AVX2] 1536x960 → 1232x770    23 ms    ← --nogpu 时走 AVX2（后台线程，不阻塞 UI）
```

优化前后对照（同一台机器、同一个 136 张的图库，间隔 350 ms 连续翻页）：

| 指标 | 优化前 | 优化后 |
|---|---|---|
| 预载档位 / 屏幕所需 | 1024 / 1196（**不够**） | 1536 / 1294（够） |
| 每张都要补解全清 | 29 次 | **1 次** |
| 单次全清解码最慢 | **1521 ms** | 不再出现在翻页路径上 |
| GPU 精修真正执行 | 0 次（位图比屏幕小，被放大判定挡掉） | 7 次，4–12 ms |
| 翻页期间 UI 冻结 | 有 | 无（仅剩启动阶段的 930 ms） |
| 预载占用 | 101 张 · 130 MB | 101 张 · 220 MB |

结论：**卡顿不在 `Go()` 的同步代码**（实测 0–2 ms，含 `ScrollIntoView` 也只有 1 ms），
而在"命中缓存后还要再解一次全清"这条链路上——预载档位比屏幕实际需要的像素还小，
于是每张图都要补一次大图解碼，大图那一下就是 1.5 秒。

### 滚轮为什么曾经比键盘慢

键盘是直接调 `Go()`，滚轮以前却要过一道「每 120 ms 最多翻一张」的定时器节流
（外加 60 ms 的刻度合并窗口）。实测快速连滚时每次切换要排队 **40–125 ms**，
还会把连续几格攒成一次跳 2–3 张，手感上就是"滚了不跟手"。

那个节流是早期为了防止「滚动快过解码 → 解码队列堆积 → 图片错位」加的。
如今切图同步只要 0–2 ms、命中预载缓存即刻上屏，这个理由已经不成立，于是：

- 翻页**不再做定时节流**，改为按 `Delta` 累积：攒够一个物理刻度（120）立刻翻，
  同一毫秒内就进 `Go()`（实测日志里 `wheel 事件` 与 `Go` 时间戳完全一致）；
- 防堆积交给新的 `DecodeGate`（`SemaphoreSlim(2)`）：最多 2 个解码同时跑，
  排队的那个拿到闸门时若发现 token 已变（页面翻过去了）就直接放弃，不做无用功。

冷区压力测试（跳到未预载处后 40 ms 间隔连滚 20 次）：只有 1 次 61 ms 冻结，
20 次切换里实际只解了 12 张——闸门和 token 丢弃都在起作用。

### 跨首尾边界（窗口环绕）

`--bench` 还有一轮**边界轮**：停在倒数第 3 张，等预载铺开后连翻 6 张跨过首尾。
这 6 次是否全部命中缓存，直接反映窗口有没有绕回。

| | 跨边界的第 1 张 | 其余 5 张 |
|---|---|---|
| `--nowrap`（窗口线性截断） | **未命中** → 低清占位 + 全清解码 | 命中 |
| 环绕（默认） | **命中** | 命中 |

本机这轮恰好都是小图，未命中那次解码只花 6 ms；但机制上是"跨边界必掉缓存"，
换成大图就是几百毫秒到 1.5 秒的卡顿（前面测过单次全清最慢 1521 ms）。

preload ready  101 张 · 367 MB · edge=1536   ← 前后各 50 张已预解码入缓存
